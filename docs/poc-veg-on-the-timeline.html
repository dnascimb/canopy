01The problem

The timeline drew flower windows only. A bar started on the flip date and ended on the harvest date. Anything before the flip was not drawn: rooting cuttings, seedlings, and plants sitting in veg waiting for a slot.

The veg tent is the space under pressure. It holds 32 and is carrying 35. The flower room it feeds is at 30 of 36. The timeline described the room with room to spare and said nothing about the one without.

02Constraints

From the brief:

“I'm concerned you're going to mess up the screen and make it more confusing when it makes perfect sense right now. Ultimately, the user shouldn't be overwhelmed, but rather have visuals used in the appropriate context. If they care about veg, we need to see that. If they care about flower, we need to see that. If they care to see the whole story, we need to see that.”
  1. The existing flower view must not change.
  2. Veg information must be reachable.
  3. The reader picks which one they are looking at.

04Design

Three views

Flower draws flower windows and is the default. Veg draws pre-flower spans. All draws both, pre-flower dimmed and behind.

A view is only offered if the data can fill it. A garden with nothing in veg gets no Veg button. All is hidden unless both kinds of span exist.

The bar is "pre-flower", not "veg"

A strict veg bar would read each plant's first vegetative event. Almost nothing has one.

The span runs from the first lifecycle event that is not the flip, falling back to the plant's started_on, up to the flip — or up to today if it has not flipped. It means "alive, not yet flowering". The label under the control says that. The span gets more accurate as more transitions are logged.

The axis belongs to the view

Server-side bounds still come from flower spans only. Pre-flower spans reach months further back, so including them would shrink every flower bar in the default view. The renderer widens the axis itself, only for the views that draw those bars. The flower view uses the server's bounds and is unchanged. There is a test for that.

06Two things this exposed

A bug the veg view made visible

The first render drew one-pixel bars against six units. The cause: a started_on entered after the fact can be later than the flip it precedes. Jack Herer was recorded as starting 7 September and flipping 4 September, giving a span of minus three days.

pre_flower_start() now returns nothing when the earliest known date is not earlier than the flip. 25 candidate bars became 19 real ones. A one-pixel bar looks like data. A gap does not.

The seeded history is now obvious

Six older groups show a pre-flower span of exactly 56 days. That is demo data: the seeder sets started_on to a fixed offset from the flip. Runs logged since the lifecycle log was added vary, as real runs do. The Veg view is the first screen that shows which parts of the history were measured.

07Limits

  • Pre-flower is one span. Clone, seedling and vegetative are not separated. The events exist in plant_events, so this is a rendering change, but it is not worth doing until more plants have those events.
  • The view is not remembered. Every load starts on Flower, so the default is always what you see first.
  • Veg load is drawn, not projected. There is no warning that the veg tent will be over its count in two weeks. That is a scheduling change, not a rendering one.
  • Nine units have no pre-flower date and draw nothing in the Veg view. They are older plants with no events and no start date.
